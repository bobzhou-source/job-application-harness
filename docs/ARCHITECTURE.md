# Architecture

This document describes how the harness is put together: the roles, the trust boundaries, the per-screen loop, and the local state it keeps. It is written for someone reading or changing the code, not for first-time setup (see [README](../README.md)).

## Design principles

- **One process, one browser connection per application.** Each CLI process owns one Chrome CDP connection for its application. `queue.mjs --workers N` runs N such processes at once (`--headless` runs their Chromes without windows), each on its own Chrome profile (`JOB_APP_PROFILE`, with its `tabs.json` beside it). Only the queue process writes the queue file. `lib/lockfile.mjs` (`withFileLock`) serialises the read-modify-write of `answers.json` and `aliases.json` across those processes. There is no broker or journal service.
- **One runner host at a time.** `runs/runner-host-lock.sh` owns the `runs/runner-host` lock. The unattended entrypoints acquire it before touching a queue or starting a pool; `runs/sync-laptop.sh` also holds it while copying private state. The laptop checkout is authoritative because the Mac has no SSH server: Mac callers delegate lock operations to the laptop over SSH, and a stale lock fails closed until an operator force-releases it. Code reaches the laptop through Git; the sync script moves ignored state and results, plus the small credential-backend files while a backend change is uncommitted.
- **Deterministic code is authoritative on safety.** Models choose among offered options; the executor validates every action against a fresh snapshot, resolves answer keys to local values, and refuses anything unsafe or unknown.
- **Eligibility is deterministic.** `lib/eligibility.mjs` reads a posting's title and description and reports a graduate level (`master`, `phd`, `mba`) only when the text requires or targets graduate enrollment; explicit bachelor's tracks and "preferred" graduate degrees stay eligible, and explicitly stated class-year windows that exclude the applicant are rejected too. The same file rejects postings that require year-round, academic-year, or fall/spring/winter-term work (with explicit remote/virtual or summer-only exceptions) and required school-year part-time commitments; summer internships and co-ops stay eligible. Discovery drops hard matches after the pay gate (`N dropped (graduate-only)` and `N dropped (academic-year/term)` in its summary) and an apply run stops `ineligible-degree <evidence>` or `ineligible-schedule <evidence>` in preflight, before its first model call. An unreadable posting page is not guessed at.
- **Models never see secrets.** Passwords and Keychain-stored credential values, the resume and transcript file paths, and raw HTML are never sent to any model, and browser URL query strings and fragments are stripped from the structured URL metadata. Visible page text and verification-email text are sent as untrusted input and may themselves display URLs. One role-specific exception: when deterministic email matching cannot safely choose a verification code, the configured planner may receive bounded verification-email sender/subject/body excerpts and candidate emailed codes (with http/https links stripped). Everything else a model receives is bounded and role-specific (see [Trust boundaries](#trust-boundaries)).
- **No applicant-specific branches.** Personal paths, facts, institutions, and model choices come from `config.json` and `answers.json`, never from hard-coded values. Vendor-specific adaptations (for example, generic handling of Workday/iCIMS/Handshake page behavior) may remain where they implement that behavior generically rather than encoding one applicant’s data.

## Roles

| Role | Who | Does | Never |
|---|---|---|---|
| **Planner** | Configured planner backend (default: native DeepSeek) | Consulted only when the driver stays stuck on a screen. Returns concrete actions on current refs, revised guidance/goals, or a stop. A note that unstuck the driver becomes a per-host lesson in `learned.json`. | See passwords; execute anything itself |
| **Writer** | Configured writer backend (default: OpenRouter model) | Composes first-person free-text answers from local facts/qa/resume within each field’s limit, and rewrites rejected ones. Accepted answers are saved to the site's `written` registry. | Answer passwords/SSN/birth date/signatures, type into a site's chat-assistant box, or answer a field that wants a recording the applicant has to make (a required one stops the run `needs-user-media`; an optional one stays empty); see passwords |
| **Grader** | Configured writer backend (same as Writer) | Grades every drafted answer and cover letter `terrible`/`ok`/`good`/`great` with a one-sentence `why` and `fix`. Drafts graded `terrible`/`ok` get one revision pass with the fix as feedback; a `terrible` answer after revision is dropped so its field is left for the user. Grades are appended to `runs/references.json`, and `great` (else `good`) entries return as the writer’s own examples. | Invent facts; block a run when grading or the store fails |
| **Driver** | Configured driver backend (OpenRouter Decisions) | Every screen: one typed request — a choice over current refs for the active goal, a goal-done probability, and field→answer-key choices. Also matches a stored answer to a dropdown option once. | Generate text/code, see passwords |
| **Executor** | Deterministic code (`apply.mjs`, `lib/*`) | Snapshot, hard gates, ref validation, local answer resolution, learned replay, credential access, trusted actions, submission confirmation. | Delegate safety to any model |

Model backends are selected in `config.json`. The public example uses OpenRouter for writer and fallback and a native DeepSeek planner. `omp` is an explicitly configured local option, never an implicit fallback; runtime code does not read private credential databases.

A planner call that its provider accepts but never answers is treated like an unpaid account: the HTTP transport bounds the whole exchange (connect, headers, and body) with one timer, and a timeout, dropped connection, 429, or 5xx switches the planner role to the configured `fallback` backend for the rest of the run (trace `deepseek-timeout`). A consult that fails (a timed-out subprocess, an unparseable plan) is retried once before the run stops with `planner-error`; the queue still halts on repeated planner errors.

Besides Handshake, the listings feed, ATS boards, markdown/JSON community lists, LinkedIn, and freehire, discovery reads the Levels.fyi Summer-2027 internship JSON (`levelsfyi`, each link resolved to the employer's own posting) and the northwesternfintech quant internship YAML directory (`quantlists`, GitHub contents API + Bun's YAML parser). `discover.mjs` gates employer-stated compensation strictly above `discovery.minHourly` at the USD/hour range floor: both endpoints are converted using weekly /40, biweekly /80, monthly /173.33, annual (including $Xk) /2080, or daily /8; a total stipend requires a stated week count on its line or in the internship program (/weeks/40), otherwise it remains unstated, and bonuses, benefits, revenue and AUM are excluded. `discover.mjs --workday` takes every Workday tenant/site seen in local runs (`summary.jsonl`, `queue-results.txt`, `applications.csv`, the queues) and searches it through the public `/wday/cxs/<tenant>/<site>/jobs` API for internship titles, dropping postings posted more than 60 days ago and titles closed to outside applicants ("Returning … Intern (For Current/Former … Interns Only)", `discover.mjs` `RESTRICTED_TITLE`, applied to every source). Within one pool, a host whose own three runs in a row did not submit is skipped for the rest of that pool (`SKIPPED host-breaker …`), its rows left in the queue for the next pool (in-memory state; a submission clears the count). ## Trust boundaries

- **Each model receives bounded, role-specific data.** The **planner** receives bounded screen data, the applicant’s facts and `qa` values, resume-derived material, and visible page text; the **writer** receives the applicant’s facts, `qa`, resume bullets, the optional `profile.md` dossier, and the field/question text, and its prose becomes the free-text answers and drafted documents; the **driver** receives bounded screen data (labels, types, options, and the current non-secret field values on the active form) plus answer key names and their current non-secret values. Passwords and credential-store values, the resume and transcript file paths, and raw HTML are excluded from every request, and browser URL query strings/fragments are stripped from the structured URL metadata. Visible page text and verification-email text are sent as untrusted data and may themselves display URLs or query strings. When deterministic email matching cannot safely choose a verification code, the planner additionally receives bounded verification-email sender/subject/body excerpts and candidate emailed codes (http/https links are stripped before that prompt).
- **Structured fills are resolved locally by key.** For a structured `fill`, a model only names a key (`facts.email`, `qa.<normalized question>`); the executor looks up the value from `answers.json`. Only the writer supplies raw text (free-text answers and drafted documents); model output can never supply a raw value for a structured fill of a stored answer.
- **Uploads are restricted.** Only the configured resume, its posting-tailored rewrite (validated against the chosen variant and the selected facts: same role headings, dates, and numbers; one page), the configured transcript (only into a transcript slot), or a writer-drafted document (cover letter, or an instructed “other documents” slot) is uploaded, and only into a current resume/document field. A lone file slot whose own label asks for another document (a writing sample, “a brief research supplement describing a relevant project”) is never the resume slot (`lib/rules.mjs` `OTHER_DOCUMENT`); its instructions are the employer's “Instructions from employer:” text, else the slot's own ask to describe/explain something (`lib/apply/plan.mjs` `instructionsOf`), and the document step composes a PDF for them before the required-document stop can hand the slot to the user. Instructions that want the resume and that document “as a single PDF” get the posting's tailored resume merged ahead of it with `pdfunite` (`lib/coverletter.mjs` `resumeBundle`, `<document>_with_resume.pdf`). A file slot's kind comes from the nearest heading above its input when that heading names a document (Workday's Resume/CV and Cover Letter sections share one wrapper, and the wrapper text alone would classify the resume slot as a cover). When one source names several kinds, the first named wins (Dow Jones's "upload any additional documents, such as resume …, cover letter, writing samples" is the resume slot). The cover-letter body is accepted at 280–500 words (the prompt asks for 320–420; the one-page build is the real limit) and the failure names the rule last broken. A cover letter the writer fails to produce is not retried on that slot (URL and label) for the rest of the run. Generated documents are cached per posting URL only while they are newer than every source they were written from (the facts file, and for a tailored resume its variant's `.tex`; for an instructed document the dossier): a source corrected after the write retires the old artifact to `stale/` and rewrites, so a withdrawn claim never keeps shipping through the cache.
- **Refs are revalidated.** Every action is checked against a fresh snapshot before it runs; a stale ref is rejected, and a queued action whose ref vanished drops the rest of that queue because the screen moved on.
- **Passwords are not a stop.** `lib/credentials.mjs` generates and fills employer-account passwords from the configured credential backend. Password values never appear in prompts, logs, snapshots, or reports. An employer account is worked as a ladder with no model guesswork: a stored password is tried once; a registration the site answers with its own sign-in form (Workday bounces a known email there without a word) or an "already registered" message means the account exists; a sign-in the site turns down ("wrong email address or password", "Invalid email address or password", "Password is incorrect") marks the host as rejected, after which registering again and re-sending that password are refused, the rules open "Forgot password", send the reset request once, follow the emailed link, set a fresh password on the reset page (stored under the same Keychain item), and sign in with it.
- **Reply tracking is local and read-only.** `mail.mjs` only issues Gmail GETs; matching and classification are fixed patterns in `lib/mail/`, so no mail reaches a model. The watcher posts employer, role, subject, and its deterministic classification to Poke for genuinely new outcomes; message bodies stay local.
- **Outreach never sends and never guesses addresses.** `lib/outreach/gmail.mjs` only creates and lists drafts. An email is used only when the address appears verbatim on a fetched public source, and that URL is stored with it. `pick` accepts only such a candidate. The drafter and reviewer receive the facts file, the recipient's paper titles and abstracts, and the configured ask. Jev receives option labels and short context. Embeddings run locally.

## A run, step by step

The loop is bounded (max 300 actions) and exits `0` for a safe terminal state.

1. **Goal.** Each run starts on one fixed goal (“complete this application”) with built-in guidance; there is no up-front planner call.
2. **Observe.** `lib/snapshot.mjs` records visible, enabled controls and fields across every frame (including cross-origin embedded forms) and open shadow roots. CAPTCHA, payment, and MFA/OTP conditions are detected as gates before any model call.
3. **Drive.** Plan sources are tried cheapest-first: an open entry of a section the stored facts say nothing about is first removed (a repeatable panel with its own Delete/Remove control — Workday's "Certifications 1" after the section's "Add" — never model-completed); then queued planner actions for this screen; then `learned.json` field replays and registry-answered dropdowns (no model call); then the writer for free-text questions; then deterministic rules (each at most once per screen), such as uploading the resume (or the configured transcript into a transcript slot) into an empty slot, clicking a posting’s only apply entry, ticking a required acknowledgement under `--submit`, and advancing with a Next/Continue step when nothing is left to fill. A file slot whose document the page already lists as attached (Workday keeps "Select files" empty after an upload and shows the file beside its Delete button) does not hold the step back.
4. **Write.** Empty free-text questions are answered up front by the writer from local facts, `qa`, resume bullets, and the optional `profile.md` dossier. Short factual questions get a plain answer; essays are drafted as candidates and one is selected. A date part under a question ("…anticipated graduation date? Month") is no text question: it takes its part of the stored date through the field mapping (`lib/apply/fields.mjs` `dateFactKey`/`dateSegment`). A graduation question (never the high-school one) and an education end/completion date take `facts.graduation`; a Proposed Start Date takes `facts.internship_start`; a month-precision fact fills a widget that demands a day with the 1st, and a text box that spells its format in the placeholder (`MM/YYYY`, `MM/DD/YYYY`) takes it in that mask. A link or handle field ("Please provide your Facebook profile:", "Portfolio URL" — `runtime.mjs` `LINK_FIELD`) is a fact or nothing: the writer never composes it (an "N/A" there is an invalid URL and a false answer), and an optional one no stored fact answers (`linkFact`: LinkedIn → `facts.linkedin`; GitHub/portfolio/website → `facts.github`/`facts.portfolio`/`facts.website`) stays empty and holds back no forward step. Text questions the `qa` registry already answers are filled from it first.
5. **Escalate.** When the driver has no plan, its fresh `none` field verdicts first recheck the deterministic forward rule: optional empty fields and placeholder dropdowns judged unanswerable on this screen do not need another driver call or a planner consult. Required fields, invalid marks, and page-issue banners still block. Otherwise, when the driver’s choice is not confident enough, or it repeats on an unchanged screen, the executor opens any empty required combobox, re-asks the driver once, then consults the planner, whose concrete actions run through the same executor checks. Consult budgets bound the loop: only a consult that changed nothing (every planned action refused, dropped, or with no visible effect, and no file attached) counts against the screen, while a run-wide cap bounds the total. Two call budgets make the loop stop on its own reason (`lib/apply/choose.mjs`, counted with `runlog.callsMade`): a plan repeated on an unchanged screen fingerprint after 23 driver calls there (`unchanged-screen-repeat`), and 160 driver calls on one form step without an accepted answer (`screen-loop`, `lib/apply/fields.mjs` `screenStep` names the step because Workday's rail re-renders and fingers the screen). Both constants come from the 2026-10-15..17 Workday traces: the p99 of calls per screen on submitted runs is 21, no submitted run spent more than 158 calls on one step without an answer, and a replay of both rules over the 904 submitted runs stops none.
6. **Execute.** Each action is revalidated against a fresh snapshot. Refused actions (back/cancel/save-for-later/destructive/payment/stale/occupied/opt-in; attestation ticks without `--submit`; a value or a picked option no stored answer states — `factless-section`, `ungrounded-option`; a generic answer such as Yes/No/I confirm/Not applicable names no entity and is exempt, since the driver derives it from the facts it was shown — an "Add" opening an entry in a section the stored facts say nothing about, and the first Next or final Submit on a screen that still has required questions empty, `advance-with-required-empty`) are skipped and the driver redrives. The factless-section guard targets entries, not questions: a disclosure question in such a section ("Have you ever held an active security clearance?", "Are you able to provide proof of U.S. Citizenship?" — `controls.mjs` `disclosureQuestion`) is offered to the driver and takes a plain stored answer (`disclosureAnswer`: a none answer always; an affirmative only from a key that does not itself name the section, since `facts.us_citizen` answers the citizenship question while a `qa.…security clearance…` = Yes would be as unverified as the section). The command-word rules vet buttons and links only: a dropdown option is an answer value ("January 2029 or later"), never a command, so it is picked whatever words it holds. An occupied choice field is re-committed once per field per screen, with the value it already holds, when the screen has demonstrably stalled (a Continue/Next/Save click that changed nothing, or a validation error). A Cancel/Close inside a modal dialog that is not itself a form and not a withdrawal/deletion confirmation dismisses that dialog; profile-section controls of the candidate’s own profile on the employer’s host navigate within it. Choice fields are opened and re-observed before matching a stored answer against their own options; every probe that types into a searchable list (an alias search, the "Other" probe when an "If other, please specify" field is on the screen) clears its text and reopens the list before the list is judged, so a probe's leftover filter never reads as an empty list. Accepted fills are verified by screen URL and field label, not transient refs; `required` is no part of a field's identity, since site validation flips it mid-batch (Workday marks a half-filled date group required) and the batch's later fills would then find no target. A stored answer strips a list's catch-all options ("Not applicable", "Other", "Prefer not to say") from the writer's choice only when it is the field's own answer — a fact, the mapping learned for its label, or a `qa` entry whose question is this field's (`picker.mjs` `concrete`); a planner's guess of a foreign key ("Are you 18" for a California-waiver select) does not, else the writer is left no honest option. A select-only list that renders its rows a beat after opening (Workday's Language list in a freshly added entry) is re-read for up to 2.4 s before its answer is judged unlisted. A required choice in a repeatable entry the run opened ("Certifications 1") whose stored answer is listed twice as unmatched is not asked of the user when the entry holds nothing else: the entry's own Delete button closes it again and the history tells the driver not to reopen it. A date box — a Month/Day/Year segment under a date question (`fields.mjs` `isDateBox`) — is never a text question: the writer never composes it, and `choose.mjs` keys every segment of one question through `fields.mjs` `dateFactKey` (graduation and education end/completion dates → `facts.graduation`, a Proposed Start Date → `facts.internship_start`, else the mapping learned for the question without its segment word), so each segment takes its own part of the stored date (`dateSegment`: "May 2029" → 05 / 01 / 2029). A date widget whose month is a searchable picker is dispatched before the plain parts of the same batch, since the month can gate the year (Greenhouse clears a year typed while its month is empty).
7. **Trace.** Every run writes a JSONL trace under the ignored `runs/` directory, named by its start time (a second worker starting in the same millisecond takes the name with its pid), and one summary row in `runs/summary.jsonl` carrying the whole posting URL: the queue's history keys on the job id at its end.

Several screen states are handled before any model sees them (`lib/apply/prepare.mjs`, `lib/apply/preflight.mjs`): a page showing only a site error banner is reloaded; a page showing only "Loading" with no fields, or only the site's own shell (header and footer, under 400 characters, no field and no apply/continue/sign-in control — Workday for a beat after "Apply Manually"), is given one 8-second wait, then up to two reloads per URL; a resume step whose file was just accepted ("successfully uploaded") but that shows nothing to fill and no way forward is given up to 90 seconds per URL for the site to parse it (Workday's autofill step moves on by itself); a Continue/Next that stays disabled with nothing left to fill gets the filled text boxes retyped once, then one reload; a Workday sign-in that lands on the signed-in candidate home or the site's job-search root reopens the posting (at most twice; a sign-in form drawn at the candidate-home address is worked, not left). An "Add" into an empty work-experience section is followed by a wait of up to 6 s for the entry's panel to render (`workhistory.mjs`): Workday draws it after a server round trip, and a re-observe inside that beat would add again. A dropdown that opens to no choices gives the planner one look with that outcome in its history (the list may need a typed search, or the entry holding it may be removable with its Delete) before the field is handed to the user. Clicks never scroll an element that is already on screen and hittable (`lib/act/resolve.mjs`): Workday prompt lists re-render on scroll and drop the click that follows.

Logging shows `PLAN <goals>` when the planner plans and `JEV <action> <label> conf=<c>` for each executed choice.

## Snapshot and refs

`lib/snapshot.mjs` returns `{ url, title, controls, fields, gates }`.

- **Controls** are `button | link | option`, each with a stable `ref`, an optional `formRef` (including external `form="<id>"` controls), a label, a form-field count, and, when the form holds password boxes, their count (`formPasswordCount`). Open custom dropdowns contribute `option` controls. A section's generic button ("Add", "Add Another", "Delete") is named by the group it acts in ("Add Another Work Experience", "Delete Certifications 1"): Workday's My Experience page otherwise shows five identical "Add" buttons.
- **Fields** carry `ref`, optional `formRef`, tag/type, label, name, `required`, `occupied`, and options. A date segment also carries its own `segment` (`month|day|year`, read from `dateSectionMonth-input`, a lone `Month`/`YYYY` aria-label or placeholder, or a spinbutton in a date wrapper), its `placeholder`, its `ariaValueNow` when the widget reports the accepted part there, and the `dateGroup` (wrapper `data-automation-id`) all of the group's segments share; a group caption that crowds a segment word past the label cap keeps the segment word, so the driver can still read the part. Password values are always empty; file values are reported as `attached` when occupied. A text box drawn smaller than a pixel (Workday's "this input is for robots only" honeypot) is not a field, unless a visible sibling display draws it (Workday's date segments: a 0 × 0 `dateSectionMonth-input` behind the "MM" display). A select-only dropdown (a non-input combobox, or a button announcing a listbox from inside a form question: Workday's `<fieldset><legend>Question</legend><button aria-haspopup="listbox">Select One</button>`) is a `select` field; one named only by its own selection ("Select One Required") takes its question as its label, and one named "question selection Required" keeps the question alone, so the executor opens it and picks from its options like any other choice field; its value is the text its box shows minus its own label and any "Select One" prompt (Workday wraps "Degree *" and the button in one short box), so an unanswered one is empty. A list a widget keeps open after its pick committed (Workday's multi-select) is closed with Escape. Fields sharing a short label (Workday's Month/Year date parts) are told apart by their group's caption: a fieldset legend, else the first visible text line of the nearest ancestor holding no other same-labelled field; the field's own value, a placeholder ("YYYY"), a 1px screen-reader announcement, and validation text ("Error") are never captions, so a date part keeps one name as it is typed; a caption is a short line (60 characters) unless it is the group's own fieldset legend, which names it whatever its length ("If you have not graduated yet, what is your anticipated graduation date?"). A date part with a generic label ("Start date year", "End date month") takes its section's caption ("Education End date year", "Employment Start date year") even when the label is unique on the screen: the nearest ancestor caption that is no field's label or dropdown prompt, within a section of at most twelve fields, so an Education block's, an Employment block's and an availability question's dates never share one learned mapping. `required` is what the site declares (`required`, `aria-required`) or shows (a "Required"/"(required)" label suffix, an asterisk element beside the label, a starred fieldset legend); class names are never read, since they name the site's implementation rather than its rules (AngularJS puts `ng-valid-required` on optional boxes too). A field the site marks in no readable way is treated as optional until the site's own validation names it ("Address2 is required", a described-by "This field is required") on an attempted step; `observe` then upgrades it to required, so the site, not a markup guess, decides what blocks a step.
- **Choice groups** (`lib/snapshot/groups.mjs`): native radios and checkboxes sharing a name form one field whose options are their shown boxes; `role=radio`/`role=checkbox` widgets form a second kind of group only when they do not wrap a shown native input (Rippling's custom radio wraps a native one), so each option ref belongs to exactly one group and a check lands on one field. A custom group whose members carry no words is no field (Workday draws a pair of unnamed `role=radio` boxes under its page footer, which read as a "© 2026 Workday" question).
- **Refs** are stable strings. Main-frame refs are `e<N>`; child-frame refs encode the frame’s CDP id (`f<frameId>:e<N>`), and shadow-root refs are resolved by traversing the open roots. Actions re-find the exact frame or reject the ref as stale. A frame whose JavaScript world does not exist yet (a child frame still loading or being torn down) is skipped — evaluating in it would wait puppeteer's 30 s per frame; a main frame without one (a full navigation in flight) is waited for up to 10 s per snapshot, after which `observe` retries the snapshot (eight times) rather than reporting an implementation error.
- **Locators** (`scan.mjs` `locatorOf`) are optional `{aid, id, name}` on fields and controls: the element's own `data-automation-id` (else its Workday `formField-*` wrapper, else its nearest non-page ancestor's; a Workday date segment, one id on every date box, is qualified by its wrapper: `formField-startDate/dateSectionMonth-input`), plus `id` and `name`. Choice groups take their first member's, or the custom group container's. `lib/family.mjs` `locatorKey` turns that into the stable key an ATS family template replays (`aid:`, then `name:`, `id:`, `label:`; a choice group's `name:` comes first), skipping generated-looking ids; the planner and JEV never see it.
- **Gates** detect captcha, payment, and MFA/OTP conditions. They are checked before filling.

## Final-submit safety

`lib/rules.mjs` classifies controls (`apply-entry`, `step`, `final-submit`, `login`, `other`). A label phrased as a question ("3. What happens after I submit my application?") is an FAQ heading or a prompt, never the action its words name (only the account prompts spelled out in `RE_LOGIN`, "Don't have an account?", keep their class). Form ownership wins: an apply-like control inside a nonempty form is a final submit regardless of its label. An account form's own button (a Submit/Continue whose form is password boxes plus at most two other fields: a password-reset page, a registration) is `login`, never the application's final submit. The executor:

- refuses any `final-submit` click unless `--submit` is set;
- clicks the final submit at most once, recording the confirmation phrases and URL the page already showed (`lib/apply/confirm.mjs` `evidenceOf`), then confirms the submission on a later screen only with evidence that was not there before the click (a standing "the position you applied for" in a privacy FAQ proves nothing) and with no submit control and no empty required field left, before reporting `SUBMITTED`;
- never ticks marketing/SMS/newsletter/job-alert/talent-pool/future-contact opt-ins;
- refuses social/third-party sign-in, cloud document pickers, passkeys, policy links that would abandon a filled form, and unrelated posting or navigation controls;
- hides date-of-birth pickers from model choice so no model picks a date.

Applications ran without `--submit` stop before the final submit and leave the page open for the user.

## Local state

All of the following are ignored by Git and stay on the machine:

- `config.json`, `.env` — local configuration and secrets.
- `answers.json` — `facts` and the reusable `qa` registry. `qa` holds only applicant-universal answers: entries you authored or edited, and option picks derived from a stored value. `written` holds the model-composed, posting-specific answers, scoped by the site that was answered (`written[site][normalized question]`, where `lib/answers.mjs` `siteKey` is the host, plus the employer's path segment on a multi-tenant ATS host such as `job-boards.greenhouse.io/<employer>`, `jobs.lever.co/<employer>`, `jobs.ashbyhq.com/<employer>`, or the posting id on Handshake); each entry is `[{ text, posting, title, t }]`, the posting id and title it was composed for; a run replays an entry as `qa.<key>` only on that posting or one with the same title (`overlaySiteAnswers`; `preflight` overlays the same-title entries once the title is read) and composes the rest fresh, so a compensation figure written for one employer's form (lib/apply/writer.mjs `writeFor`, `rememberForSite` in `lib/apply/accounts.mjs`) never reaches another employer's, and an interest-area pick made for one posting ("Tolls" for a toll-technology internship) never reaches the employer's other postings. A legacy bare-string entry replays nowhere until `report.mjs --site-answers --annotate` pins it to the posting the ledger says composed it. `written._unattributed` parks entries whose site is unknown; nothing replays them.
- `profile.md` — optional writing dossier.
- `learned.json` — accepted field mappings, choice aliases, per-host lessons, and `noAnswer` optional-field labels (skipped by the forward rule and by Jev's field questions, even if an older learned mapping exists). Fresh `none` verdicts also skip optional fields and placeholder dropdowns by ref for the exact screen fingerprint in this run, including fields with no learnable label; neither kind of skip bypasses required fields. `families` holds ATS family templates: `lib/family.mjs` maps a host to its family (Workday, Greenhouse, …), and each field or forward step is keyed by its locator (`data-automation-id`, then `name`, `id`, or label) with hit/miss counts. `lib/apply/template.mjs` confirms a recording on the next snapshot (empty, invalid, or non-advancing counts a miss) and replays an entry only while hits exceed misses, so a later tenant of the same family fills known fields with no model call. Controls are recorded in two roles: `next` (a Next/Continue step) and `open` (a model-chosen click on a screen with nothing to fill whose locator is the site's own automation id: Workday's "Apply Manually" among the apply options), replayed only on a screen with no fields. A locator several fields on one screen share (Workday repeats `formField-jobTitle` for every work-experience entry) names none of them and is neither recorded nor replayed; those fields keep the per-label mappings. Read-modify-writes go through `lib/lockfile.mjs`.
  Searchable dropdowns use the same learned/registry/template path as other fields: the executor still commits a listed choice, and the next snapshot must confirm it before learning. Only one searchable widget is planned per observation, so the executor's one-widget limit does not consume other widgets' replay guards. A confirmed family choice also records its full per-question label and key; a later tenant need not share the locator. Requiredness is never added to that identity. Site-written answers remain posting-scoped, and ambiguous locators, work-history routing, secret/type exclusions, hit/miss trust, and once-per-field replay guards stay intact. `lib/apply/questions.mjs` keeps the same decisions tenant-free: a question is keyed by its normalized text plus its sorted normalized option set (a free-text box by its text alone, `text`), never by tenant, locator, or ref, and names never enter the store. A Workday tenant mints its own questionnaire ids but asks the same questions, so an answer confirmed on one tenant replays on any other of the family with no model call; every replay still passes the executor's guards (controlled work-rights/age/EEO/salary/GPA questions are answered by the policy first and are never read from or written to this store), and hit/miss counts stop one the site rejected from replaying.
- `aliases.json` — equivalent forms and site-accepted alternatives for facts.
- `tabs.json` — posting→tab resume state (under `JOB_APP_PROFILE` when a worker sets it).
- `queue.tsv`, `runs/` — queued work, per-run traces, logs, and reports; `runs/mail.json` holds the last mail sync (indexed job email, to-dos, posting status, outreach threads, and the cached text and links of indexed mail), `runs/mail-done.json` the to-dos you marked handled, and the watcher keeps `runs/mail-watch.json` (seen events, pending sends, digest day, knockout flags), `runs/mail-digest.txt`, and `runs/knockout-flags.tsv`.
- `runs/references.json` — every graded answer and cover letter (`{t, host, title, question, kind, answer, grade, why}`), appended by `lib/planner/grader.mjs`: the writer’s own-best examples (`great`, else `good`, same kind, chosen by token overlap with the current question) and the reviewable history of what was submitted.

## Configuration flow

`lib/config.mjs` is the single source of configuration. It parses and validates `config.json`, rejects unknown keys, expands `~` and repo-relative paths, and exposes a cached, deeply frozen normalized object. Consumers call `loadConfig()` and `requireSecret(name)`; they do not read `config.json` or API-key environment variables directly, and there is no consumer-side defaulting or path expansion.

`applicant.workAuthorizedCountries` (default `["United States"]`) lists the countries where the applicant may work without sponsorship or a permit. `lib/work-authorization.mjs` infers each posting's country from its text and URL once the posting body has rendered (`preflight` waits for it: a half-loaded Workday shell carries only the site chrome): the short lines at the top of the page and right under the title (wherever a cookie banner or site header pushes it), country names in the body beside a location marker (`locations`, `based`, `office`; never "based on market capitalization"), the URL slug and ccTLD, and a city/province/state map; site language labels ("English (United Kingdom)") never count, the tail of a head-and-tail-capped page text (the employer's "About Us" footer) is not read, and a tie or no evidence keeps the default United States. The decision is logged as `WORK RIGHTS posting in <country>: …` and indexed by the answer ledger; `report.mjs --suspects` flags one that names another country on a posting whose URL places it in the US. `applyPostingPolicy` in `lib/apply/values.mjs` rebuilds the per-posting answer view from the stored answers. Work-right answers (`facts.work_authorization`, `facts.sponsorship`, and the matching `qa.*` keys) are rewritten for the posting's country, or for the country a question names; US postings and questions with no non-US country keep the stored answers. The same module derives age questions from `applicant.dateOfBirth` and `facts.internship_start` (under/younger-than/minor questions are answered from the comparison, not from `facts.at_least_18`), and inverts any stored boolean answer when the question's polarity is the opposite of its stored `qa.*` (or `facts.*`) key. The picker, plan resolution, choose step, writer option list, and the pre-submit `assertApplicationAnswers` all use this policy; a contradiction stops as `wrong-answer polarity <label>` (work rights keep `wrong-answer workauth <label>`), and an age question without enough birth-date/intake evidence stops rather than guesses. The writer receives `applicant.workAuthorization` and `job.country`.

`lib/controlled-answers.mjs` extends that same expectation/option/match contract to fact-determined labels no model may answer: salary/pay/compensation free text takes the stored `facts.pay_expectation` range in the field's unit (hourly or annual, inferred from the label or options; annual when neither says), salary bands must contain the stored floor or be the lowest band at or above it, and a filled salary below the floor stops as `wrong-answer salary <label>`; GPA bands/percentages must contain the stored GPA (a percentage derives from the stored GPA and scale) and a band that excludes it stops as `wrong-answer gpa <label>`; veteran, military, disability, race/ethnicity, and gender choices use the exact stored status (or a decline option when one is required) and stop on a contradiction as `wrong-answer veteran|disability|eeo <label>`; legal/preferred first, middle, last, and full names come only from the matching `facts.*` name (falling back between preferred/legal variants only within the same field semantics), never from another name fact or a learned template; and a "majoring in one of the listed disciplines" yes/no is computed from `facts.major`, stopping on a contradiction as `wrong-answer major <label>`. The writer resolves these fields before any model call, the picker/Jev/execute paths select only a fact-valid listed option, family templates neither record nor replay name fields, and a required controlled field whose fact is absent stops as `unknown-answer <family> <label>` rather than guessing.
